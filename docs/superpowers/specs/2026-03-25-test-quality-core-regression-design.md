# F1 Express 第一阶段测试与质量设计

日期：2026-03-25
主题：核心链路防回归
状态：待评审

## 1. 背景

当前项目已经具备基础测试体系：

- `tests/unit/` 用于纯逻辑与 hook 测试
- `tests/integration/frontend/` 用于页面与交互测试
- `tests/integration/server/` 用于 Express 接口测试

但从现状看，测试仍存在三个问题：

1. 核心链路覆盖不均衡
   例如更新链路前端页面仍有明显空白，而部分旧页面测试已经落后于当前行为。
2. 回归保护集中在少数模块
   一旦数据同步、运行时更新或关键页面筛选发生变化，仍可能依赖手测发现问题。
3. 覆盖率报告口径失真
   `dist/`、`public/` 等产物被计入覆盖率，导致总数字不能真实反映源码风险。

本设计只解决“核心链路防回归”，不追求一次性做成全面测试治理工程。

## 2. 目标

第一阶段目标：

- 为最容易出事故的核心链路建立稳定回归保护
- 优先覆盖真实业务风险，不以总覆盖率数字为导向
- 在不大改业务代码的前提下，补齐关键测试缺口

非目标：

- 不追求全项目高覆盖率
- 不做视觉快照型回归体系
- 不在本阶段引入过重的测试抽象或大规模重构
- 不将所有质量门禁一次性卡入提交流程

## 3. 方案对比

### 方案 A：风险优先型

只补关键业务链路的回归测试，覆盖数据加载、2026 同步、关键页面行为、更新接口。

优点：

- 投入小，见效快
- 与当前“防回归”目标最一致
- 对现有架构侵入最小

缺点：

- 边缘模块仍会存在空白
- 总覆盖率提升不会特别显著

### 方案 B：页面优先型

优先补主要页面的渲染、搜索、切换与空状态测试。

优点：

- 用户可感知路径更完整
- 前端层面反馈直接

缺点：

- 页面文案与结构变化会让测试更脆
- 对底层同步与服务端保护不足

### 方案 C：底层优先型

优先补数据同步与服务端接口测试，页面层只保留少量烟雾测试。

优点：

- 底层稳定性提升明显
- 对逻辑回归保护更强

缺点：

- 页面交互缺陷仍可能漏掉
- 用户主流程保护不够完整

推荐结论：

采用方案 A，即“风险优先型”。

## 4. 范围

第一阶段只覆盖以下四类链路：

### 4.1 数据入口

目标文件：

- `src/utils/f1Data.ts`

关注行为：

- 数据库来源优先级
- 缓存失效与坏库回退
- 运行时依赖缺失时的错误表现

### 4.2 2026 同步

目标文件：

- `src/utils/f1-data/season2026.ts`

关注行为：

- 本地与远端数据择优
- 远端空结果不覆盖本地有效结果
- `forceRefresh` 行为
- 资源失败时的降级

### 4.3 关键页面

目标文件：

- `src/pages/DriversPage.tsx`
- `src/pages/RacesPage.tsx`
- `src/pages/DataManagementPage.tsx`

关注行为：

- 默认筛选是否符合当前产品逻辑
- 搜索是否真正影响列表
- 关键空状态与错误态是否可见
- 更新页的请求状态转换是否正确

### 4.4 更新接口

目标文件：

- `server/routes/updates.cjs`

关注行为：

- 鉴权校验
- 配置缺失时的拒绝逻辑
- Docker socket 缺失时的错误返回
- 更新任务是否被正确调度

## 5. 不纳入本阶段的内容

- `AnalyticsPage`、详情页等大页面的全面补测
- 视觉快照测试
- 原子组件逐个补齐
- E2E 自动化
- Python 数据管线的新增系统测试
- CI 强制覆盖率阈值

这些内容可以进入后续第二阶段，但不放进当前设计。

## 6. 测试设计原则

### 6.1 只测稳定行为

优先验证：

- 输入输出
- 角色与状态
- 关键交互结果
- 错误与降级路径

避免大量依赖：

- 易变的中文文案碎片
- 纯样式 className
- 组件内部实现细节

### 6.2 单测与集成测试职责清晰

单测负责：

- 数据选择逻辑
- 缓存逻辑
- 错误降级
- 纯函数/模块行为

集成测试负责：

- 页面主流程
- 用户可见状态切换
- 服务端接口行为

### 6.3 最小必要 mock

要求：

- 网络边界、浏览器 API、外部依赖可以 mock
- 不把页面状态流全部 mock 成空壳
- 尽量保留真实组件组合关系

### 6.4 不为测试而重构业务

本阶段允许做的代码调整：

- 极小的可测试性改动
- 明显错误测试断言修正

本阶段不做：

- 为了“更好测”而拆大块业务逻辑
- 测试驱动的大范围架构重写

## 7. 实施顺序

建议顺序如下：

1. `DataManagementPage`
   原因：页面层最明显空白，且直接连接更新链路
2. `AppUpdater`
   原因：与更新页属于同一业务能力，适合一起补齐
3. `server/routes/updates.cjs`
   原因：补齐前后端更新链闭环
4. 覆盖率口径整理
   原因：让后续质量判断基于真实源码，而不是构建产物
5. 剩余关键页面边界补测
   原因：在主链路稳住后，再向外围扩张

## 8. 验收标准

第一阶段完成标准：

- `npm run test` 稳定通过
- 新增测试直接覆盖真实高风险链路
- 核心链路至少有一层测试保护
- 更新链路前后端测试闭环形成
- 覆盖率报告中，关键模块不再是完全空白

不作为本阶段验收标准的内容：

- 总覆盖率达到某个固定百分比
- 每个页面都必须有测试
- 所有低覆盖文件都被补齐

## 9. 风险与应对

### 风险 1：测试对文案过度敏感

表现：

- 文案微调导致大量测试误报

应对：

- 优先使用角色、状态、可见行为断言
- 仅在关键业务提示上使用文本断言

### 风险 2：mock 过重导致测试失真

表现：

- 测试通过，但真实页面/接口协作仍可能出错

应对：

- 页面测试保留真实状态流
- 只在边界层 mock 网络与环境

### 风险 3：为补测试扩散到无关重构

表现：

- 范围失控，交付延迟

应对：

- 严格按“核心链路”边界推进
- 发现结构问题时单独记录到下一阶段

## 10. 下一阶段候选

如果第一阶段顺利完成，第二阶段可考虑以下方向：

- 更新链路全面补测与前端交互细化
- 覆盖率统计口径治理
- `AppUpdater` 与 `DataManagementPage` 相关可测试性轻量改造
- 页面异常态与空状态统一测试标准

## 11. 当前结论

第一阶段采用“风险优先型”测试策略，只做核心链路防回归，优先覆盖：

- 数据入口
- 2026 同步
- 关键页面主流程
- 更新接口

这样可以在最小投入下，最快降低未来改动的回归风险。
